Agent payments in AgentWeb are built around bounded authority, not raw card access. Your agent never holds card numbers or initiates a charge independently. Instead, the user approves a scoped payment authority — defining the merchant context, amount limit, currency, expiry, and revocation path — and the agent operates strictly within that envelope. Checkout itself happens on a Dodo-hosted page in the user's browser.

## The payment flow

<Steps>
  <Step title="Discover payment rules">
    Your agent reads the payment metadata published at `/.well-known/agent-commerce.json` for the target domain. This file signals Dodo checkout support, OAuth metadata, and ACP/UCP integration-target information.
  </Step>
  <Step title="User approves payment authority">
    Present the payment authority scope to the user before proceeding. The authority must include:
    - **Principal** — the agent provider and business identity
    - **Scope** — the specific operations allowed (e.g. `price.setup`, `create.checkout_session`)
    - **Amount limit** — maximum value and interval (e.g. single-use)
    - **Currency** — the approved currency code
    - **Expiry** — when the authority lapses
    - **Revocation URL** — where the user can cancel the authority independently
    - **Receipt and verification requirements** — whether proof of completion is mandatory
  </Step>
  <Step title="Create a checkout session">
    Call the `agentweb_create_checkout_session` MCP tool with the approved authority. The tool returns a handoff URL that signs the customer into Dodo-hosted checkout for the selected plan.

    <Note>
      `POST /api/billing/create-checkout-session` is a separate REST endpoint available only to the customer's own signed-in web session — it cannot be called with an `aw_` API key. Agents must use the `agentweb_create_checkout_session` MCP tool exclusively.
    </Note>
  </Step>
  <Step title="User completes checkout in browser">
    Open the handoff URL in the customer's browser. The checkout page is Dodo-hosted — your agent does not interact with it directly. The redirect to a confirmation page is not proof that payment succeeded.
  </Step>
  <Step title="Webhook verification">
    Dodo sends a signed webhook to AgentWeb after the transaction settles. AgentWeb verifies the `webhook-id`, `webhook-signature`, and `webhook-timestamp` against the raw request body before applying any credits or entitlements.
  </Step>
  <Step title="Agent receives receipt">
    After webhook verification completes, your agent receives a structured receipt artifact containing the merchant, amount, currency, transaction reference, status, source, and timestamp. This is the authoritative proof of completion.
  </Step>
</Steps>

<Warning>
  Agents must never collect raw card numbers in conversation or pass them as action parameters. A checkout redirect to a confirmation page is **not** proof of entitlement — your agent must wait for webhook verification before treating a payment as complete.
</Warning>

## AgentWeb Card

Pro and Max plan users can enroll a payment card directly in the AgentWeb dashboard and use it for agent-initiated purchases.

<CardGroup cols={2}>
  <Card title="Device-bound enrollment" icon="shield-halved">
    Cards are enrolled with a device-bound passkey. The raw card number is never exposed to the agent or stored in conversation context.
  </Card>
  <Card title="Per-purchase limits" icon="gauge">
    Set a per-purchase limit and a daily limit. Each individual transaction mints a one-time card number scoped to that purchase, preventing reuse.
  </Card>
</CardGroup>

<Tip>
  Per-purchase and daily limits give you practical spending control without blocking routine tasks. Raise or lower limits in the dashboard at any time without changing any agent configuration.
</Tip>

## Credits vs. purchases

AgentWeb distinguishes between two types of charges:

- **Credits** — pay for action execution on the AgentWeb platform. Failed actions are automatically refunded. Credits are added after webhook verification completes.
- **Purchases** — charges made against your enrolled AgentWeb Card for agent-initiated transactions on third-party sites. These follow the delegated authority and limit rules above.

## Protocol discovery

AgentWeb publishes machine-readable payment metadata at several well-known URLs that agents and integration tools can inspect programmatically.

| File | What it signals |
|---|---|
| `/.well-known/agent-commerce.json` | Dodo checkout support, OAuth metadata, authority schema reference |
| `/.well-known/payment-protocols.json` | ACP/UCP integration-target signals |
| `/.well-known/mpp.json` | Machine payment profile |
| `/.well-known/x402.json` | x402 payment protocol profile |

ACP/UCP-native settlement can be added behind the same authority and verification contract. The boundary remains the same: AgentWeb does not ask agents to send raw card data or unrestricted payment-provider credentials regardless of the settlement protocol in use.

## Safety boundaries

Every payment request must carry a complete authority artifact — principal, scope, amount limit, currency, expiry, revocation URL, receipt requirement, and verification requirement. An incomplete authority is refused before any side effects occur. Unsupported, expired, or over-limit requests return a structured refusal, not a best-effort partial execution.
